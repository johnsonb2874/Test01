# SIPOC｜旅行社獲客網站推薦流程

- **負責角色：** 網站企劃／網站工程師
- **輸入：** 本課程指定的 SIPOC 範圍、`research/travel-data.json`、`research/sources.md`、`docs/weekly-report.md`
- **產出：** 本文件；界定推薦服務的供應者、輸入、處理、輸出與顧客
- **資料查詢日期：** 景點資料 2026-10-28；週報報導期間 2026-10-22 至 2026-10-28
- **待確認：** 旅行社實際商品、成本／報價、諮詢服務時段、客服管道與活動資料更新責任人
- **驗收狀態：** 通過（流程符合指定 SIPOC；營運細節待確認）

## SIPOC 概覽

| 欄位 | 定義 | 本專案落地方式／限制 |
|---|---|---|
| **Supplier 供應者** | 旅行社、交通部觀光署、活動主辦單位 | 旅行社提供經確認的商品和諮詢流程；觀光署及主辦單位提供旅遊情報與活動公告。引用時保存來源網址及查詢日期，並遵守資料使用條款。 |
| **Input 輸入** | 旅遊資料、客戶偏好、行程條件 | 旅遊資料含景點、地區、特色、客群建議、雨天適配狀態、活動日期、狀態及來源；偏好含對象、預算、天數、風格及選填的雨天優先；條件含預計日期、活動／營運限制等。缺資料要標示「待確認」。 |
| **Process 流程** | 選擇需求 → 比對方案 → 生成推薦 | 先檢查資料狀態與必要條件，再篩選符合的候選資料、排序並說明理由；雨天優先只把來源明確支持的室內／部分室內候選排前，未核實者標「雨天適配待確認」；無足夠資料支撐的條件不得假裝已匹配。 |
| **Output 輸出** | 旅遊提案、行程介紹、諮詢內容 | 第一版提供候選景點／提案、推薦理由、來源及查詢日期、待確認清單和諮詢行動入口；不承諾售價、可訂位或成團。 |
| **Customer 顧客** | 親子、情侶、熟齡旅客 | 以旅客自述偏好為準，不由年齡推斷體力、健康狀況、興趣或支付能力。 |

## 流程邊界與交接

1. **需求選擇：** 旅客選擇旅遊對象、每人每趟預算、天數、風格及可選日期。頁面說明預算單位，避免團體總價與每人金額混淆。
2. **資料檢查：** 網站工程師／內容維護者確認候選資料有唯一 ID、狀態、查詢日期、來源和推薦欄位。過期、無來源或待確認欄位不可當作已核實條件。
3. **比對候選：** 以硬性條件先篩選，再按對象適配、風格標籤等可用資料排序。價格、交通、活動日期或天數欄位缺漏時，該項只能標為待確認，不能推定符合。
4. **生成推薦：** 逐筆展示已核實特色、建議理由、資料狀態、來源及查詢日期。適配度如以分數顯示，必須標為系統排序參考，不可說成客觀品質或成功機率。
5. **諮詢交接：** 旅客可複製提案或開啟旅行社諮詢管道（管道待確認）。諮詢前再次查核時效資訊，並由旅行社確認商品、價格、供應與預訂條件。

## 交接驗收

- 研究員交付來源完整、狀態明確的景點資料給網站工程師；不完整項目列待確認。
- 週報編輯交付經查核的主題文案和引用給網站工程師；時效事實保留來源及查詢日期。
- 網站工程師交付需求表單、推薦卡片、無匹配狀態與操作說明給驗收員。
- 驗收員確認每個輸出可追溯、預算口徑清楚、沒有隱藏式放寬條件，並把未執行的檢查標為「待確認」。
