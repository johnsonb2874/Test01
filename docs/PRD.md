# PRD｜旅行社 AI 獲客與智慧行程推薦網站（第一版）

- **專案名稱：** AI 台灣旅遊情報員 × 智慧行程推薦網站
- **文件負責角色：** 網站工程師（依旅遊研究員、週報編輯與網站企劃交接）
- **文件狀態：** 第一版需求規格，已於 2026-10-28 增補「雨天優先」需求；品牌、營運及正式行程商品資料尚待旅行社確認
- **輸入：** `AGENTS.md`、`research/travel-data.json`、`research/sources.md`、`docs/weekly-report.md`、`docs/CCI.md`、`docs/SIPOC.md`
- **產出：** 網站建置與驗收規格
- **內容查詢日期：** 2026-10-28；週報報導期間：2026-10-22 至 2026-10-28
- **已知資料限制：** 目前 9 筆均為常態景點基本資料，`activity_dates` 為空值；沒有可用的售價、營業時間、交通班次或可售行程。適合客群是研究員建議，不是官方認證。雨天欄位僅能根據來源明確寫出的室內／戶外設施描述整理，不代表天候或當日營運保證。
- **待確認：** 旅行社品牌與聯絡方式、實際行程商品、報價與成本資料、商品可售日期、正式客服管道、內容更新負責人及隱私告知文案。
- **驗收狀態：** 待確認（雨天優先與原有流程之 Node VM 回歸測試 10/10 通過；實際瀏覽器版面／裝置檢查仍待確認，見 `acceptance/website-index.md`）。

## 1. 目標

### 產品目標

1. 透過每週旅遊情報吸引親子、情侶與熟齡旅客瀏覽。
2. 讓旅客以旅遊對象、預算、天數和風格快速找到可考慮的候選提案。
3. 用可見的來源、查詢日期、資料狀態和待確認說明，建立可信的諮詢起點。
4. 引導旅客複製提案或聯繫旅行社，完成獲客流程的下一步。

### 第一版成功條件

- 旅客可完成需求填寫、候選比對、查看推薦理由與來源、發起／準備諮詢。
- 價格等資料缺漏時，網站如實表明無法確認預算是否符合，不顯示虛構數字。
- 沒有符合方案時，說清楚無匹配原因，讓旅客自行選擇要調整的條件。

第一版不訂定轉換率、營收或客戶滿意度目標，因目前沒有基準數據；未來如建立目標，須標明資料期間及實際量測方式。

## 2. 使用者

| 使用者 | 主要需求 | 產品注意事項 |
|---|---|---|
| 親子旅客 | 依同行對象、孩子年齡區間、興趣與步行需求找候選行程 | 不假定特定設施、動物或活動當日可用；只詢問推薦必要的最少資訊。 |
| 情侶旅客 | 依景觀、文化、散步或城市體驗偏好比較選項 | 氛圍描述屬提案文案，不宣稱官方認證或保證體驗。 |
| 熟齡旅客 | 依個人興趣、步行／休息／無障礙需求找候選 | 不從年齡推斷健康或行動能力；路線可及性未查核時標「待確認」。 |
| 旅行社業務／內容維護者 | 用來源完整的資料回應諮詢並確認時效欄位 | 不把網站候選提案當作可售商品、正式報價或已預訂行程。 |

## 3. 範圍

### 第一版包含

- 靜態多頁或單頁網站，以 **HTML、CSS、原生 JavaScript** 建置。
- 旅遊情報入口、需求表單、推薦結果、來源／資料狀態展示及諮詢行動。
- 以本專案 `research/travel-data.json` 作為初始景點資料來源。
- 本機 JavaScript 比對與排序；不需登入、資料庫、伺服器端推薦或外部 API。
- 手機、平板、桌面響應式版型及鍵盤可操作的基本無障礙行為。

### 第一版不包含

- Supabase、資料庫、帳號註冊、會員偏好保存、雲端部署或個人化追蹤。
- 即時票價、庫存、交通班次、天氣、訂位或付款功能。
- 旅行社正式商品管理、後台 CMS、正式報價／成團承諾。
- 未有已授權素材的圖片再利用或未經核准的活動資訊匯入。

## 5. 功能需求

### F1｜需求表單

- 必填：旅遊對象（親子／情侶／熟齡，可複選）、每人每趟預算（NTD／人／趟）、天數、旅遊風格（至少一項）。
- 選填偏好：勾選「雨天優先」後，將有來源明確支持的室內／部分室內景點排前；其他偏好相符但雨天條件未查核的景點仍可列於後段，並標「雨天適配待確認」。此選項不預測天氣、不保證全程遮雨或當日開放。
- 選填：預計出發日期、地區偏好、步行或無障礙需求、自由文字補充。
- 表單應能清除／重設條件，並清楚標示哪些是必填。
- 不要求姓名、電話、Email、身分證字號、精確生日或健康診斷。若需安排諮詢，由旅行社另行取得必要聯絡資訊並告知用途。

### F2｜推薦結果與理由

- 顯示推薦名稱、地區、已核實特色、對應的偏好條件與推薦理由。
- 客群適配欄位標示為「行程建議」或「推薦參考」，不要呈現為官方認證。
- 顯示資料狀態、查詢日期、來源名稱／網址及待確認欄位。
- 啟用雨天優先時，在推薦理由中說明排序依據及雨天適配狀態；必須提供支持該欄位的來源及查詢日期。
- 可按關聯度排序；若結果不適用旅客條件，提供更改條件操作。

### F3｜預算與金額呈現

- **計價單位：每人每趟新台幣總預算（NTD／人／趟）**，由旅客自行輸入可接受上限。
- 此預算定義為旅客希望控制的整趟個人支出上限；但目前資料沒有任何成本、票價、交通或住宿估價，網站不得計算總價或標示「符合預算」。
- 當方案資料缺少價格時，結果卡應顯示：「價格尚未確認，暫時無法判斷是否符合每人每趟預算；請洽旅行社確認。」
- 未來若導入正式報價，須逐筆記錄幣別、計價單位、包含／不包含項目、適用人數／日期、報價來源、查詢日期與有效期限。沒有上述欄位時不參與預算過濾。
- 若家庭旅客希望以多人總額規劃，第一版可在說明中提醒先換算每人上限；多人總額模式列為待確認的後續需求，不與每人單位混用。

### F4｜找不到符合方案的處理

- 若硬性條件篩選後為零筆，顯示「目前找不到符合全部條件的方案」，並列出未匹配原因（例如所選風格沒有已標記資料、預算缺少報價資料、天數尚無方案資料可判斷）。
- 提供可選操作：取消某一個風格、改選地區、放寬日期、調整天數，或保留條件改為人工諮詢。操作需由使用者主動選擇。
- 旅客的預算條件若因來源缺少價格而無法判斷，不能以「符合預算」篩選；應呈現「預算尚無法核對」狀態，可推薦其他欄位相符的候選並明確提醒。
- 不得自動放寬必填條件、把相似推薦包裝成符合、捏造行程或以模擬報價補空缺。

### F5｜資料狀態、過期與待確認欄位

- 每筆資料至少保留 `id`、`data_status`、`queried_at`、`source_ids`／來源網址，以及各待確認欄位的狀態或說明。
- 狀態詞彙使用「已驗證」「待確認」「資料已過期」「模擬資料」。模擬內容不得混入正式推薦，除非使用醒目「教學模擬」模式。
- **頁面時效政策（第一版建議規則，需由內容負責人核准）：** 景點名稱、地區及一般特色查詢日期距瀏覽當日超過 30 個日曆日，標「資料已過期，請重新查核」；若尚未有核定更新週期，視為產品營運規則而非外部事實。
- 價格、營業時間、預約、交通班次、活動日期、施工、安全及開放狀況屬高時效欄位；第一版無來源／刷新時間資料，預設不顯示確定值並標「待確認」。若後續引入此類資料，更新當日也須保留來源及查詢日期；正式出發／成交前再次核實。
- 雨天適配是從來源描述衍生的輔助欄位，不等於即時天氣資訊或官方雨天推薦。僅在來源明確記錄室內／戶外特性時設定「室內」或「部分室內」；其餘使用「待確認」，不得依景點類型自行猜測。欄位須包含依據文字、來源 ID、查詢日期及限制說明。
- 活動日期已過時標「活動日期已過」並從可參加活動候選中排除；活動日期為空值或來源未明時標「活動日期待確認」。常態景點沒有活動日期時標示「非特定期間活動」，不能當成日期缺漏或當前活動。
- 待確認狀態須貼近欄位值顯示，例如「交通班次：待確認」「無障礙路線：待確認」，另在卡片底部列出查核提醒。
- 查詢日期缺漏、來源連結缺漏、來源無法對應該項事實時，不得標成「已驗證」；改列待確認並避免作為硬條件推薦依據。

### F6｜諮詢與資料處理

- 第一版可提供「複製提案摘要」及待確認資訊清單；聯絡連結與表單由旅行社提供後再啟用。
- 未建後端前，偏好僅在瀏覽器當次工作階段處理，不寫入伺服器或第三方分析工具；若實作使用瀏覽器儲存，需明確告知並提供清除方式。
- 所有文案說明「推薦為規劃參考，價格、日期、營運與供應以旅行社及官方最新確認為準」。

## 6. 推薦邏輯

### 欄位匹配順序

1. 先排除狀態為「模擬資料」、缺少來源或已過期且尚未複核的記錄。
2. 依旅客選擇的旅遊對象，與 `recommended_audiences` 比對；其符合僅代表研究員建議，不是保證。
3. 依旅遊風格與資料 `highlights`、`type` 等已維護標籤比對。第一版若尚未建立正式 `style_tags`，需依明確的人工映射設定；不可由自由文字臆測。
4. 若開啟「雨天優先」，對已符合旅伴及風格條件的候選先依 `weather_suitability.status` 排序：來源已核實「室內」優先於「部分室內」，兩者優先於「待確認」。雨天待確認項目不因開啟此選項而自動排除，但須清楚標示且不得宣稱適合雨天。無來源依據或資料過期者不可取得雨天優先權。
5. 地區、日期及天數僅在資料具備相應欄位且已查核時作篩選。當前資料未提供完整行程長度或活動日期，這些條件只能顯示「待確認／無法判斷」。
6. 預算只在每人總價、幣別、包含項目和有效日期均已驗證時做區間比對。目前沒有價格資料，因此所有景點候選都不標為預算符合。
7. 對剩餘候選依匹配到的對象與風格排序，展示排序依據，不必顯示容易被誤讀為精準機率的百分比。

### 推薦解釋文字

使用可追溯格式，例如：「推薦參考：你選擇『親子探索』；研究資料列出此景點有兒童遊樂園區特色。適合度屬研究員建議。來源：……（查詢日期：……）。」如果是由網站分類標籤而非來源原文支持，需標「網站分類／提案」。

## 7. 資料欄位

### 旅遊資料（現有資料與第一版建議欄位）

| 欄位 | 型別／範例 | 必要性 | 用途與規則 |
|---|---|---|---|
| `id` | 字串，如 `TW-ATT-0001` | 必填 | 唯一識別碼。 |
| `name` | 字串 | 必填 | 景點或行程名稱。 |
| `region` | 字串 | 必填 | 地區；沿用研究資料。 |
| `type` | 字串 | 必填 | 景點／區域遊程／活動／正式行程等。 |
| `highlights` | 字串陣列 | 必填 | 來源支持的特色；逐項可回溯來源。 |
| `recommended_audiences` | 字串陣列 | 可選 | 研究員建議客群，畫面需標成建議。 |
| `audience_fit_basis` | 字串 | 可選 | 說明客群建議的依據與非官方認證狀態。 |
| `style_tags` | 字串陣列 | 建議新增 | 網站篩選標籤；每個標籤須有維護定義／負責人。 |
| `weather_suitability` | 物件 | 建議新增 | `status` 為「室內／部分室內／待確認」；並記錄 `evidence`、`source_ids`、`queried_at`、`limitations`。不得以未查證的室內印象推論。 |
| `activity_dates` | 日期／日期區間／`null` | 活動必填；常態景點可空 | 空值要區分「非特定期間活動」與「日期待確認」。 |
| `price` | 數值或 `null` | 可選 | 只有正式來源、幣別、單位、包含項目及有效期限完整時才能用於預算匹配；目前不存在。 |
| `price_currency` | 字串 | 有價格時必填 | 第一版目標幣別為 NTD。 |
| `price_unit` | 字串 | 有價格時必填 | 如 NTD／人／趟；不得只存裸數字。 |
| `price_inclusions` | 字串陣列 | 有價格時必填 | 說明包含與不包含項目。 |
| `duration_days` | 整數／範圍／`null` | 行程建議新增 | 景點資料無法自動推導天數；無行程來源時留空。 |
| `data_status` | 列舉 | 必填 | 已驗證／待確認／模擬資料／資料已過期。 |
| `queried_at` | `YYYY-MM-DD` | 必填 | 查詢日期；無日期則不得標已驗證。 |
| `sources` 或 `source_ids` | 來源陣列／ID 陣列 | 必填 | 來源名稱、直接網址及支持欄位；對應 `research/sources.md`。 |
| `pending_fields` | 欄位名稱與原因陣列 | 建議新增 | 明確列出日期、價格、交通、可及性等待確認項目。 |
| `last_reviewed_at` | 日期 | 建議新增 | 內容維護者重新檢查日期；與原始來源查詢日期分開。 |

### 旅客偏好（僅當次計算）

| 欄位 | 型別／單位 | 必要性 | 資料最小化原則 |
|---|---|---|---|
| `audiences` | 親子／情侶／熟齡陣列 | 必填 | 以自我選擇為主，不從人口資料推定。 |
| `budget_per_person_per_trip` | NTD 數值 | 必填 | 每人每趟總預算上限；顯示價格無法確認時的限制。 |
| `duration_days` | 天數 | 必填 | 不把天數轉換為未驗證的景點停留時間。 |
| `style_tags` | 標籤陣列 | 必填 | 從已維護選項選取。 |
| `rain_priority` | 布林值 | 選填，預設 `false` | 啟用時只改變有來源支持的室內程度排序；不作天氣預測，不保證雨天適用。 |
| `travel_date` | 日期 | 選填 | 只用於提示時效查核；無活動日期資料時不判定可參加。 |
| `accessibility_needs` | 選填文字／選項 | 選填 | 僅收集規劃需要的需求；避免健康診斷細節。 |

## 8. 響應式版型與可用性

- **手機（窄螢幕）：** 單欄卡片、表單欄位滿寬、主要 CTA 易點擊；來源和狀態資訊可折疊，但狀態標籤需始終可見。
- 雨天優先控制沿用可換行的偏好標籤列；窄螢幕時自動換行，不壓縮或遮住原有旅伴、風格選項。
- **平板：** 需求表單維持單欄或雙欄，結果卡依螢幕寬度調整為一至兩欄。
- **桌面：** 主內容置中；可採左側條件區與右側結果區，來源及待確認內容在結果卡內可直接閱讀。
- 所有版型避免只用顏色區分已驗證／待確認；搭配文字標籤與圖示替代文字。
- 表單可鍵盤操作，焦點明顯；欄位有可讀標籤、錯誤訊息與語意化 HTML。
- 頁面支援窄螢幕閱讀，長來源網址以連結名稱顯示，不造成水平捲動。

## 9. 安全、隱私與技術限制

- 僅使用 HTML、CSS、原生 JavaScript；不加入 Supabase。
- 前端不得放密碼、API Key、權杖或真實個資。第一版無需任何秘密憑證。
- 靜態 JSON 可公開瀏覽的內容不得包含旅客私密資料或內部成本。
- 第三方圖片、文字或資料使用前確認來源條款與授權；未確認素材標示待確認並暫不發布。
- 本機執行資料若沒有更新管道，頁面需明示資料查詢日期，不能暗示即時資訊。

## 10. 驗收條件

| 編號 | 驗收條件 | 驗收方法／預期結果 |
|---|---|---|
| A1 | 技術符合第一版限制 | 確認以 HTML、CSS、原生 JavaScript 運作；沒有 Supabase、帳號或未要求的後端。 |
| A2 | 偏好表單完整 | 可選旅遊對象、預算、天數、風格；欄位標籤、必填提示和重設操作清楚。 |
| A3 | 預算單位清楚 | 表單明示「每人每趟新台幣總預算（NTD／人／趟）」；現有資料無價格時明確顯示無法判斷預算是否符合，不生成金額。 |
| A4 | 推薦理由可解釋 | 每張結果卡可看見依據是已驗證景點特色或系統／研究員建議；客群適配不標示為官方認證。 |
| A5 | 找不到匹配處理正確 | 零筆時說明原因並提供手動調整條件選項；不靜默放寬、不捏造替代商品。 |
| A6 | 資料狀態及過期處理 | 顯示已驗證／待確認／模擬／過期狀態；超過核定新鮮度規則的資料標過期。30 日建議規則未核准前須明示為暫行產品政策。 |
| A7 | 來源與日期可查 | 每筆旅遊事實可查看來源名稱、直接網址和查詢日期；缺漏即不得標「已驗證」。 |
| A8 | 時效欄位不誤導 | 空日期、無價格、交通或營運資訊標「待確認」；已過活動不得顯示為未來活動。 |
| A9 | 響應式與鍵盤操作 | 在手機、平板、桌面檢視無水平溢出；可用鍵盤完成表單與結果操作，焦點清楚。 |
| A10 | 個資最小化 | 推薦流程不要求不必要個資；偏好不未告知地傳送或保存。 |
| A11 | 機密安全 | 前端程式碼、範例及公開資料沒有密碼、API Key 或權杖。 |
| A12 | 未執行檢查如實紀錄 | 驗收紀錄使用通過／未通過／待確認；未做的操作或裝置測試不得推定通過。 |
| A13 | 雨天優先有依據且可解釋 | 僅將來源明確記載的室內／部分室內候選排前；待確認候選標示清楚且不冒稱雨天適用；關閉選項時原有排序與篩選不變。 |
